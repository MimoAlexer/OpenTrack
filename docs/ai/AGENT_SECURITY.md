# Agent isolation and security policy

The agent is an untrusted code generator operating on untrusted repository content. Tests, hooks, dependency scripts, configuration, MCP servers and generated binaries are all code execution. The trusted boundary consists of controller, credential broker and publication service; a runner host is a separately revocable trust domain. [Threat register](../SECURITY_ARCHITECTURE.md), [lifecycle](AGENT_LIFECYCLE.md).

## Execution profiles

| Profile | Intended use | Required boundary | Supported claim |
| --- | --- | --- | --- |
| Core installation | Issue tracking, no repository execution | API/worker nonroot containers | Full core functionality without agents |
| Trusted-owner runner | One operator's explicitly trusted repositories | Rootless container on separate runner host, namespaces, seccomp/AppArmor, cgroups, no host mounts/socket | Limits accidental damage; does not guarantee containment of hostile code against kernel escape |
| Untrusted repository runner | Public repos, other contributors, mixed users | Disposable VM/microVM per attempt, restricted network and ephemeral disks; controller/broker outside | Stronger isolation subject to hypervisor/host patching and attack tests |

Docker's [rootless mode](https://docs.docker.com/engine/security/rootless/) reduces daemon/runtime privilege; it is not a replacement for a VM trust boundary. Initial product can ship only the trusted-owner profile if it clearly limits scope and keeps it disabled by default; it must not advertise hostile multi-tenant agents until the stronger profile passes M12 gates. VM engine choice is Q03 and blocks untrusted execution, not core release.

## Filesystem and process controls

Attempt filesystem contains only checkout, scratch, temporary runtime state and explicitly allowed readonly toolchain caches. No /home host mount, SSH agent, Docker/Podman socket, cloud instance credentials, host /proc view, Kubernetes service token or production volume. Root filesystem readonly, work/scratch quota-bound, no privileged mode/capabilities, no host networking/PID namespace. Environment is allowlisted rather than inherited. Runtime caches use content-addressed readonly inputs or separate per-trust-scope storage to prevent poisoning.

Network-disabled checkout preparation is separate from allowed repository fetch: trusted fetch broker obtains approved repository snapshot, verifies ref/SHA and supplies it to sandbox. Dependency downloads need explicit registry/host policy and still execute within the sandbox. Git hooks and repository-discovered tool/plugin configuration are disabled where the runtime supports it; if the runtime cannot prevent unsafe discovery, isolate it and decline unsupported capabilities rather than assume ignoring prompt instructions is sufficient.

## Network and secrets

Default execution egress denied. Named destinations may include provider broker and explicitly approved dependency registries, with DNS resolution and destination IP checks enforced by network policy/proxy. Deny RFC 1918/private/link-local/metadata/loopback destinations except exact admin-configured local inference broker paths. Domain allowlists need redirect/DNS-rebinding protection and TLS validation. Do not permit arbitrary CONNECT tunnels or host networking.

Keep permanent OpenAI/Anthropic/Git keys and OAuth refresh tokens outside execution. A run may receive a short-lived broker credential scoped to attempt, provider, model, request ceiling and deadline; assume repository code can read it. The broker is not a general HTTP proxy: restrict destination, methods, API path, request size and budget, and revoke immediately on lease/grant loss. This limits but does not eliminate abuse within the granted budget. A CLI that cannot operate through an approved credential boundary is not enabled for hostile repositories until a safe adapter exists.

Repository read credentials are used by trusted fetch outside sandbox; remote write credentials only by trusted publisher after review. Do not place long-lived key environment variables into a process that launches arbitrary child commands, even if output redaction exists. Session storage generated by optional runtimes is encrypted at rest or destroyed after attempt according to retention; it is never uploaded as a normal log artifact.

## Grant and approval calculus

Effective permission = current OpenTrack membership ∩ repository grant ∩ provider grant ∩ runner profile ∩ run-specific capability set ∩ current lease. A model can request an additional capability but cannot approve it. Grants name paths/actions/network/resources/deadline explicitly; permission prompts cannot collapse to Allow everything. Default allowed effects are modify attempt checkout and run approved validation under the sandbox. Default denied effects are host file access, arbitrary external network, personal credentials, branch write, PR creation, merge, deploy, database access and modification of CI permissions.

Review approval binds user,run,attempt,repository,base/head SHA,patch digest,test-manifest digest,policy/grant hash,action and expiry. Before executing a write, recheck every binding and current reviewer authority. Reviewer sees if tests failed or were not run. Enforce separation of requester/reviewer when workspace policy requires it. A changed artifact, changed policy, rebase or expired approval invalidates the grant; no approval is inherited by attempt N+1.

## Data handling and residual risk

Issue/repository content is untrusted even when it looks like instructions from an admin. Treat tool outputs as data. Sanitized provider output cannot control host commands or pick credentials. Logs are access-controlled, bounded and scrubbed for known secrets; no redaction system guarantees elimination of arbitrary secret-like content. Keep prompts/source out of default telemetry and support bundles.

A model given source can disclose that source through its permitted provider request. Users must see the provider/data destination and approve inclusion. An attacker may misuse a run-scoped inference credential within its remaining budget; monitor unexpected request shapes and rate. A compromised runner can forge logs/test results, so repository CI and human code review remain independent evidence. The controller cannot guarantee an unpatched hypervisor or malicious host operator is safe.

## Security test gate

Use purpose-built hostile fixtures: traverse/symlink artifact paths; read host canary; enumerate /proc environment; reach metadata/private DNS; launch fork/memory/disk bombs; poison cache; install malicious dependency; execute repository hook; forge log terminal event; replay old fence; alter approved patch; request hidden workspace through tool; publish without grant; leave grandchild after cancellation. Test denied effects by independent host/network observations, not only application error messages. Require failure containment and cleanup evidence before enabling the corresponding profile.
