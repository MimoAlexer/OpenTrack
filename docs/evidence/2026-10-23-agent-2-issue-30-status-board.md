# Issue 30: status-board increment

This increment adds a team-scoped board to the existing issue list. It implements status movement, not manual rank or project/cycle boards. Issue 30 and its inherited M04/M05 acceptance remain open.

## Behavior and compatibility

The display selector preserves ordinary filters and ordering through issue open/close, reload and Back. `layout=board&display_version=1` is presentation state; those parameters never enter the issue API query. Unsupported display versions require an explicit repair. A board requires a selected accessible team and never substitutes another team.

List and board use the same authorized issue query and canonical issue rows. Board pages replace at most 50 cards instead of appending; switching from an accumulated list refetches a real first page rather than truncating rows while retaining a later cursor. At most five status columns render at once, with navigation to every current column. Priority ordering remains within status columns. Counts and empty states describe the current page, not a total scope. Page controls retain keyboard focus through loading and exhaustion.

Pointer movement and the keyboard-accessible Move dialog share the existing conditional issue PATCH: only `status_id`, the canonical issue ETag and current CSRF token are submitted. Drag activates after 6 pixels, or a 200 ms touch hold; Escape, short gestures, same-status drops and outside cancellation do not write. A selected issue must be closed before moving that same card, preserving its independent editor draft.

Rust continues to enforce current authority, team/status scope, archive rules and reopening/assignee eligibility. Targets require a current authorized workflow. Stale and rejected moves retain their requested destination, load current authorized state and require explicit Review then Apply. Unknown transport outcomes require a read before another command. Successful canonical overlays survive until the refreshed page arrives; failed moves do not restore an obsolete whole collection. Permission denial purges cards and cached team/status context and aborts/fences older reads. Same-team refreshes and filter changes retain that concealment. Explicit retry restores the board only after a fresh page and an unconditional, matching-team workflow read both succeed; an empty authorized issue page alone does not prove private-team access. An unavailable assignee projection remains distinct from an unassigned issue.

No schema, API DTO, native route or worker capability changes are introduced. Migration 0026 is unchanged. Rollback uses the matching previous frontend; existing issue mutations remain durable ordinary commands, with no automatic reversal or destructive migration.
