# Issue-list selection and keyboard focus

Date: 22 October 2026. Scope: issue #17 and focused-list navigation in issue #18/F21. Implementation base: integrated main `de1caaf`, including accepted PRs #141 and #142; synchronized with `8e3186e` before publication. The intervening PR #143 changes only its event-consumer contract test and evidence, leaving the tested production/frontend sources unchanged. No server, wire, schema or authorization change.

## Behavior

A pending title search could navigate back to the list after an issue was opened. The routed component regression failed against the unchanged implementation: after opening the real row link and advancing the pending timer, the selected issue URL became the list URL. Pausing that debounce while an issue is selected cancels the unwanted navigation. Explicitly closing the detail resumes the pending query while preserving team, sort and existing list context. The isolated list suite then passed all 12 tests.

Focused rows now support bounded Up/Down and Home/End across the rendered groups. Enter and Tab retain native link behavior. Modified keys, AltGraph, composition events and non-row controls are excluded from row navigation.

Closing detail restores the originating row or its nearest surviving neighbor in the original display order. Without an available original neighborhood it uses the first remaining row; an empty list uses the actual workspace heading. If a delayed list refresh removes the restored row afterward, recovery waits for that exact result to commit and rechecks request generation, scope, authority and cancellation. A surviving control's focus is preserved.

The [saved keyboard case](../../web/e2e/keyboard.browser.ts) creates three durable issues and navigates their actual links using browser keyboard actions. It archives through the UI, holds the real list response, closes detail while the original row remains, then releases the unchanged server response. It verifies durable archive state, row removal and focus on the next neighbor, previous neighbor and finally the heading. The test fabricates no API response and uses no arbitrary delay.

Independent review found no actionable findings in the integrated production/browser changes or merged component tests. Review was read-only and did not execute tests. The lane's isolated runtime and shared verification/browser locks cover the corresponding execution; raw credentials and runtime diagnostics remain private and ignored.

The three timed-out replacement jobs subsequently succeeded in one attempt with no retry/error. Their measured queues were 39.53, 43.61 and 40.48 seconds; the corresponding attempts took about 16, 20 and 8 ms. The retained private runtime had 34 registered workspaces. These observations establish delayed dispatch, not a precise scheduler-stage cause or a new focus regression. The source uses bounded registry scans and five rotating stages, but their individual latency was not measured. The private harness then selected the existing supported `--worker-poll-interval-ms 250` setting for faster test dispatch. Production defaults and the browser's 30-second wait remain unchanged. The targeted pass does not establish default-config dispatch/performance qualification or isolate the earlier queue delay to one stage; those gates stay open.

The final complete run exited successfully with a fresh receipt of all 108 passing cases. Its API and worker remained alive through testing, and the owned runtime stopped before the browser lock was released. This establishes the tested 250 ms configuration only; the default-config dispatch observation above remains unresolved.

## Acceptance boundary

These results establish the specific browser and component behaviors above. They do not qualify a physical keyboard layout or OS IME, screen-reader browse mode, native desktop GUI, all core keyboard tasks, performance, full F21/M03 or whole-product completion. Issues #17 and #18 remain open for their full criteria and dependencies. The separately prepared priority/Trash browser cases are not part of this increment's committed coverage.

No persistent-data rollback is needed. Reverting the frontend changes restores the prior selection/focus behavior. Hosted checks and exact-head integration review remain required before acceptance on main.
