# Team settings and saved workflow/taxonomy qualification

Date: 22 October 2026. Scope: issue #14 and the selected-team exceptional-state portion of issue #12, based on integrated main `d01fb0c`. No migration, server authorization or wire contract changes.

## Product correction

Team settings previously searched only the loaded directory page for `team_id`. A real isolated workspace with more than 50 teams proved that the requested team was readable through the API, while its settings form never opened. The [sanitized failure receipt](2026-10-22-agent-1-issue14-before.json) records that failing browser assertion.

The selected team now loads through its own scoped resource, independently of directory pagination or failure. Saving refreshes both resources so a second edit uses the new version. Workspace/account changes discard old results; same-account password confirmation retains the draft. A selected-team 403/404 removes its cached sidebar name/key immediately and refreshes the directory. A transient 503 retains separate retry behavior. These loading, denial, retry and stale-response cases have deterministic component coverage; this does not claim a real browser access-revocation scenario for the settings panel.

The [saved regression](../../web/e2e/team-settings.browser.ts) creates an isolated workspace and selects an authorized team absent from the actual first 50 rows. All three engines open the form without paging, save twice with a reload between saves, and verify the durable name and two version increments. The [positive receipt](2026-10-22-agent-1-issue14-team-settings.json) records 3/3 passing cases against the production build.

## Saved browser workflows

The four [workflow/taxonomy cases](../../web/e2e/workflow-taxonomy.browser.ts) use the real Rust API, PostgreSQL and restricted workflow worker:

- Light appearance persists through reload. Status creation, rename/color, explicit order saving and a changed default persist. UI issue creation omits an explicit status and receives the new server default. A persisted replacement survives reload, finishes through the real worker, exposes completed progress, preserves the issue identity and restores the source status under its original ID without moving the issue back.
- Label restoration receives real HTTP 409 and 412 responses. The proposed name remains until explicit conflict review and retry with the current version; the independently occupied label remains intact.
- A shared directory pages through 105 saved labels in exact order without duplicates or omissions, then resets to a narrowed query. This is functional pagination evidence, not a large-workspace performance measurement.
- Removing a member's private-team grant makes their issue read return 404 while the historical assignee remains ineligible. Restoring the archived issue requires an explicit eligible-assignee repair. A concurrent restore/archive produces HTTP 412; the UI retains the repair, requires review, saves an explicit unassignment, and reloads the same durable result. The revoked member still receives 404.
