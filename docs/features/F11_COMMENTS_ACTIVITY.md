# F11 Comments and activity history

Stage: MVP. Delivery: [M04_COLLABORATION](../milestones/M04_COLLABORATION.md). Related: [product contracts](../PRODUCT_SPECIFICATION.md), [data](../DATABASE_DESIGN.md), [API](../API_DESIGN.md).

## 1. Purpose and user value

Keep decisions and attributable changes beside the work so a later reader can reconstruct what happened.

## 2. Functional requirements

Approved expansion obligations: X16, X61, X63. Their acceptance behavior and delivery mapping in [REQUIREMENTS_STATUS](../REQUIREMENTS_STATUS.md) are part of this feature contract, including extensions beyond its original release tier.

Rich-text comments, mentions and subscriptions. Author edits own comments; moderation creates audit evidence. Activity tracks meaningful changes with actor/time and before/after summaries. Deleted comments show tombstones; activity is not security audit.

## 3. Interaction patterns

Chronological feed with newest at bottom, load older on request, separate comment composer, edited marker and permalink. Group adjacent low-value property changes without erasing individual events.

## 4. Data requirements

comments, documents, revisions, activity_entries and issue_subscriptions. Immutable change records; sensitive before/after content omitted from general metadata.

## 5. API requirements

Comment create/update/delete and cursor activity list. Comment creation has idempotency; edit uses document/comment version contract defined per endpoint.

## 6. Authorization rules

Issue readers see its discussion; writable contributors comment. Only author or authorized moderator edits/removes; team privacy applies to all linked mentions.

## 7. Edge cases

Mention removed user, edit comment while another reads, deleted parent issue, oversized paste and notifications generated by later edits.

## 8. Failure behavior

Failed send preserves draft and status. Unknown outcome retries same key. Edited mentions only notify newly added eligible recipients, never repeat all old mentions.

## 9. Performance considerations

Page 25 feed items; lazy-load revision bodies; no full issue history in list payload. Grouping happens in rendering, not lossy DB compaction.

## 10. Feature dependencies

F04, F06, F12 editor, F19 notifications, F30 moderation audit.

## 11. Acceptance criteria

F11-A1: repeat submit creates one comment. F11-A2: changing status leaves attributable history in same commit. F11-A3: unauthorized edit is rejected and does not alter body/version.

## 12. Testing strategy

Author/moderator matrix, mention diff and dedupe tests, comment conflict E2E, tombstone/permalink accessibility and paginated history tests.

## Implemented activity behavior

Manual issue updates capture only changed field names, with before/after facts for status, priority, estimate, due date, archive state, assignee IDs and label IDs. Status names are captured while the team lock is held; later status renames do not rewrite history. Title and description changes retain their field names only. Both activity endpoints omit historical title/body and unknown metadata from their projections, while retaining the current-issue and recorded-team access checks. No historical rows are rewritten.

The timeline shows safe facts, actor and time. It describes assignee state and label counts without resolving historical identities or inaccessible labels. Workflow replacement and system access cleanup have distinct wording. Older records without facts remain readable without invented values.

Rendering groups at most five adjacent manual priority/label/estimate/due-date updates by the same stable actor within two minutes of the first event. Status, content, archive, assignment, comments, workflow jobs, system actions and unattributed legacy events break a group. Native expandable details preserve every event, its facts and timestamp. Pagination remains 25 durable events per request; refresh or access changes invalidate pending older-page responses.

This change needs no migration. Deploy matching API/frontend contracts together. Rolling back application code restores the older projection behavior, including its historical metadata exposure; it does not erase the newly stored facts.
